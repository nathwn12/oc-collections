# oc-bifrost

An OpenCode plugin for anyone still running legacy plugins: it runs V1-era plugin hooks on the OpenCode V2 runtime, which otherwise hard-rejects a V1 module at load. Each hook is translated one by one against a compatibility matrix, and anything with no faithful V2 destination is refused out loud instead of silently dropped.

## Quick start

To use it, add one bridge entry to the `plugins` array of the OpenCode config; the host resolves and installs the package itself, so there is no separate install step. Use the bare name (a pinned entry names a version that does not exist between a bump and its publish) and give it exactly one specifier from one of the four paths (`github:`, `preset:rtk`, local file, registry package):

```jsonc
{
  "plugins": [
    {
      "package": "@nathwn12/oc-bifrost",
      "options": {
        "plugins": ["<one specifier>"],
        "strict": false,
        "verbose": true
      }
    }
  ]
}
```

Then verify what actually resolved — these two commands are the ones `INSTALL.md` prescribes:

```sh
opencode plugin check     # re-resolves online
opencode plugin list      # shows what is actually loaded
```

Route floors, all per `INSTALL.md`: `github:` needs oc-bifrost 0.4.0 or later; registry specifiers need 1.6.0 or later; `preset:rtk` needs the `rtk` binary (>= 0.23.0) on `PATH`. Confirm the host is OpenCode V2 first (`opencode --version` reports `2.x`) and read the config path from `opencode debug paths` rather than assuming a default location.

To work on it, from this package's directory (`packages/oc-bifrost` in the monorepo; the monorepo root works too with `-w @nathwn12/oc-bifrost`) — only the scripts `package.json` declares:

```sh
npm run check       # typecheck + compile + tests; must be green before a PR
npm run compile     # emit to dist/
npm run typecheck   # no-emit typecheck
npm run test        # node test runner over test/*.test.js
```

| `src/report.ts` | The honesty layer — full/partial/refused reporting |
| `src/sink.ts` | Durable report mirror — the file that survives discarded stdout |
| `src/` | Bridge sources compiled by `tsconfig.json` (`rootDir: src`, `outDir: dist`) |
| `test/` | Node test runner; imports from `dist/` |
| `vendor/` | Vendored third-party code, byte-identical to upstream (see `vendor/README.md`) |
| `docs/` | Design specs and plans |
| `dist/` | Build output; regenerated by `npm run compile` (and by `npm run check`); ignored by the monorepo root `.gitignore` |
| `index.ts` | Repo-root re-export of the plugin entry for path-based loading |
| `package.json` | Manifest: scripts, peer, published file list |
| `INSTALL.md` | Agent-first setup page; its version pins always equal the manifest version |
| `CHANGELOG.md` | Per-release changelog, kept current with every change |
| `PROOF.md` | Dated end-to-end verification record; history, not a living doc |
| `VERIFIED-PLUGINS.md` | Plugins smoke-tested through the bridge, with the route each row exercised |
| `CONTRIBUTING.md` | The two contribution doors: hook coverage and verified plugins |

## Conventions

- Commit subjects are conventional (`docs:`, `fix(scope):`, `chore(scope):`, `chore(release):`) and every PR lands as one logical change — see `CONTRIBUTING.md`.
- Branch as `<type>/<slug>`, land only through a pull request, squash-merge, then delete the branch.
- `npm run check` must be green before review; the matrix is the contract and if the docs disagree with it, the matrix wins.
- Never claim `full` without a test that exercises the write-back (the load-bearing case is `tool.execute.before`: the host reads back the mutated input after the hook, so an in-place mutation reaches execution).
- Verify against the host source and cite by `file:line`; a refusal is a valid contribution, faking a bridge is not.
- Keep `CHANGELOG.md`, `INSTALL.md`, and the docs current with every change; no new runtime dependencies without a reason stated in the PR body.

## Host contract

- Targets the OpenCode V2 runtime: the host provides plugin loading, the `plugins` array config surface, and the `@opencode/plugin` API the bridge registers against (peer `2.1.1`, so the host supplies it). The host needs Node 22 or later.
- What the host provides versus what the repo ships, as `package.json` states it: the peer above comes from the host; the repo ships zero runtime dependencies (no `dependencies` field) and bundles the vendored preset plus its docs in the published file list.
- What the bridge translates between API versions: V1 hook keys become V2 registration calls (`src/hooks.ts`); the V1 `PluginInput` facade (`src/context.ts`); the shell facade (`src/shell.ts`). Modules route by shape — V1 factory / V1 module bridges hook by hook at the matrix level (`full` = bridged with write-back, `partial` = bridged with a stated loss, `unsupported` = refused out loud, never faked); a V2 `{ id, setup }` definition mounts as-is exactly as the host would mount it; an Effect-only `{ id, effect }` definition is refused out loud. Anything unmapped warns at load and `strict: true` aborts instead.

## Release

- npm tracks `main` 1:1: every fix lands on `main` and ships as the next patch — there is no slow/stable track here.
- In the monorepo, releases are cut by pushing the package tag `@nathwn12/oc-bifrost@<version>`; the root `release` workflow triggers on `**@*`, requires the tag version to equal `package.json` and be strictly newer than every published version, and publishes over OIDC. A `v<version>` tag does nothing.
- The changelog lives in `CHANGELOG.md`.
- `dist/` is build output and is not committed in the monorepo — regenerate it with `npm run compile`; `npm publish` runs `prepublishOnly` (`npm run check`), which compiles first.

## Guardrails

- Never add an npm script named `install`, `postinstall`, `preinstall`, `build`, `prepare`, or `prepack`: npm runs those automatically on install or publish, and this package has no setup step — `package.json` carries none of these names.
- `INSTALL.md` documents the bare `"@nathwn12/oc-bifrost"` entry; `test/package-entry.test.js` fails if an exact `@x.y.z` pin reappears there — a pinned entry names a version that does not exist between a bump and its publish.
- Keep `PROOF.md`'s dated evidence as history rather than rewriting it: it records what was verified and when, and rewriting it would present old verification as current.
- Never edit the vendored `vendor/` tree by hand: it is certified byte-identical to upstream in `vendor/README.md`, so hand edits silently break provenance — refresh it only through the vendoring script.
